# Как создаём новые страницы Opten

Версия 1.0 · 13.10.2026 · правила этого проекта.

Процесс состоит из двух самостоятельных этапов: **креативный директор → агент
сборки в свежем контексте**. Эти документы уже находятся в репозитории; повторно
прикладывать клиентские файлы 01/02/03 не нужно. Общие инструкции принадлежат
`AGENTS.md`, визуальная база и активные направления — `DESIGN.md`.

## Команды пользователя

| Запрос | Действие агента |
| --- | --- |
| «Новая страница: …», «Хочу сделать страницу …» | Выполнить [02](02-CREATIVE-DIRECTOR.md), сохранить направление и предложить свежего агента сборки |
| «Подготовь направление для …» | Только этап 02 |
| «Собери страницу по этому направлению …» в свежем чате | Выполнить [03](03-START-PAGE.md) по указанному файлу |
| «Создай новый чат и стартуй страницу по …» | Создать свежий чат этого же проекта и передать точный путь к направлению и стартовый запрос |
| «Поправь отступ/заголовок/иконку на существующей странице» | Адресная правка по текущей системе, без полного 02 |
| «Зафиксируй правила» | Обновление документации, без новой страницы и генераций |
| «Напиши SEO-статью» | Существующий SEO2-процесс из `AGENTS.md`, без подмены креативным этапом |
| Явное поручение пройти всё в одном запуске | Выполнить разрешённую последовательность; это исключение из обычного разделения |

Имеющиеся pipelines моделей, Learn и курса сохраняются. Добавление контента в
существующий формат не означает заказ нового UI. Новое продуктовое поведение
не возникает из одной иллюстрации или идеи директора.

## Что сохраняем в Opten

- React 18, TypeScript, Vite 6, Tailwind 4, React Router и существующие библиотеки.
- Главная — источник визуального языка сайта; дополнительные страницы получают
  собственную композицию внутри этой системы, а не обязательную копию Hero.
- Unbounded и PT Root UI в существующих локальных variable WOFF2; Inter в своей
  области. Не заменять их static-файлами по правилу клиентского шаблона.
- Текущие контейнеры, адаптив и RU/EN. Основной просмотр сайта — 1512 CSS px;
  мобильный — 390 px, дополнительный узкий контроль — 360 px. Это ширины QA,
  а не новые фиксированные размеры каждого блока.
- Общие `SiteHeader`, `SiteFooter`, `InstallButton`, `AiAccessButton`, текстовые
  роли, семейства карточек и проектная графика. Реальные файлы/API проверяются.
- Для расширения — его отдельная система. Дизайн popup не переносится на сайт
  автоматически; изменение расширения требует явного поручения и его контекста.
- Auth, billing, ограничения маршрутов, SEO, Learn и курс — по своим контрактам.
  Для публичной индексируемой страницы нужны RU/EN, prerender и регистрация по
  `docs/CONTENT-AUTHORING.md`; для закрытой/noindex — соответствующая SPA-политика.

Astro, `.astro`-компоненты, client islands, резерв 1728px, desktop-only и запрет
реального продуктового поведения из клиентского шаблона здесь не действуют.
Не создавать альтернативный сайт, готовую тему или проектные adapters/skills.
Технические инструкции инструментов обязательны; внешние дизайн-методики
применяются только по прямому запросу пользователя.

## Где лежат результаты страницы

Только для действительно заказанной страницы создаётся каталог
`docs/page-workflow/pages/<page-slug>/`:

- `VISUAL-DIRECTION.r01.md` — самостоятельный результат директора; следующие
  показанные редакции получают свободный номер.
- `CONTENT.md` — только если ещё нет канонического текста в `src/content/`,
  переводах или другом назначенном источнике. Не создавать независимую копию.
- `ASSETS.json` — сведения о реально произведённых/выбранных файлах, когда
  появляются новые медиа; планируемые слоты пока остаются в направлении.
- `REVIEW.r01.md` — при сборке: предъявляемая ревизия, результаты, отклонения
  от гипотез и реальные ограничения проверки.

В `DESIGN.md` хранится одна запись страницы: route, область, ссылка на активное
направление, рабочая/показанная/принятая ревизии и статус. Полный текст, числа
tokens и реестр медиа не размножаются по документам. Старое имя
`VISUAL-PLAN.md` поддерживается без обязательного переименования.

## Передача в свежий контекст

Директор завершает этап файлом и самодостаточным стартовым запросом из
[шаблона](templates/VISUAL-DIRECTION.md). В нём есть точный путь/ревизия,
route/область, канонический контент, связанные контракты и условия показа.
Сообщения текущего чата не должны быть обязательным входом для сборки.

В конце директор **предлагает** «Начать сборку в свежем чате». Он не запускает
03 автоматически и не создаёт чат только ради такого предложения. После
прямого поручения создать чат используется новый локальный чат в сохранённом
проекте `C:\Projects\opten-website`. Нужен тот же checkout с доступными файлами
направления, а не новая ветка/worktree без этих незакоммиченных материалов.
Fork с историей не является свежим контекстом. Публикация и коммит из передачи
не следуют.

На этапе 02 работает один агент в роли директора. На этапе 03 другой агент
самостоятельно читает пакет, оценивает реализуемость и качество. «Креатор»,
«критик» и «проверяющий» внутри одного этапа — последовательные проверки,
не фиктивная команда; автоматические параллельные субагенты не требуются.

## Что означает готовность

`READY_TO_BUILD` — направление достаточно конкретно для сборки, без утверждения
дизайна пользователем. `NEEDS_INPUT` — назван обязательный пробел; независимая
часть подготовлена. `DRAFT` — полезная стартовая идея ещё не готова.
После реализации отдельно фиксируются `IMPLEMENTED`, `AGENT_VERIFIED` и
`REVIEW_PENDING`; `USER_APPROVED` относится только к прямо принятой ревизии
и области. Написанный промпт или статус не заменяют полученный и просмотренный
файл. Готовая страница не означает автоматическую публикацию.

Ранее сохранённый `READY_TO_EXPLORE` означает ту же готовность направления,
не согласование: новую редакцию ради переименования статуса создавать не нужно.

Адаптация опирается на клиентские 01/02/03 версии 7.2 и решения пользователя
от 13.10.2026. Все необходимые рабочие правила перенесены сюда; исходные файлы
на Desktop не являются зависимостью процесса.
