# План реализации режима «Вайбкодинг» в генераторе промптов

**Дата:** 2–3 августа 2026 года
**Статус:** реализовано; после production-регрессии добавлен no-op refund hotfix
**Основной репозиторий:** `C:\Projects\opten-website`
**Связанный backend:** `C:\Projects\promptscore-proxy`

## 1. Цель

Добавить в существующий генератор промптов на лендинге режим «Вайбкодинг» для Codex, Claude и Gemini.

Режим должен очищать пользовательский запрос: делать его короче, понятнее и удобнее для coding-агента, не добавляя требования, которых не было во входном тексте.

## 2. Зафиксированное продуктовое решение

Интерфейс карточки не перерабатывается.

- В первом существующем селекторе рядом с `Изображение` и `Видео` появляется `Вайбкодинг`.
- При выборе `Вайбкодинг` второй существующий селектор показывает `Codex`, `Claude`, `Gemini`.
- По умолчанию сайт по-прежнему открывается в режиме `Изображение` с текущей моделью по умолчанию.
- Для `Вайбкодинг` модель по умолчанию — `Codex`.
- Заголовок, размеры карточки, textarea, нижняя панель, счётчик, кнопки `Скопировать` и `Улучшить`, состояния загрузки и ошибок остаются на своих местах.
- Результат, как и сейчас, заменяет текст в том же textarea.
- Новые формы, вопросы, вкладки, модальные окна, дополнительные панели результата и отдельный экран не добавляются.
- RU/EN-поведение сохраняется; английская метка первого селектора — `Vibe coding`.

## 3. Семантический контракт очистителя

### Разрешено

- удалять слова-паразиты, повторы и лишние вводные конструкции;
- исправлять грамматику, пунктуацию и порядок слов;
- объединять дублирующиеся требования;
- разделять длинную нечитаемую фразу на короткие предложения или пункты;
- переставлять уже названные требования в более понятном порядке;
- сохранять исходный текст без изменений, если он уже короткий и понятный.

### Запрещено

- добавлять стиль и оценочные характеристики: `современный`, `минималистичный`, `профессиональный` и подобные;
- придумывать функции, страницы, поля, состояния, роли или пользовательские сценарии;
- выбирать стек, framework, библиотеку, provider, архитектуру или способ деплоя;
- добавлять acceptance criteria, тесты, команды проверки, этапы работы или Plan Mode;
- добавлять ограничения и non-goals, которых не было во входе;
- менять язык запроса без явного выбора пользователя;
- удалять исходные требования, технические идентификаторы или важные оговорки;
- превращать короткий запрос в техническое задание.

### Главный инвариант

Каждый смысловой элемент результата должен иметь источник в исходном тексте пользователя. Если улучшение нельзя сделать без догадки, endpoint возвращает исходный запрос.

Пример:

```text
Вход:  Сделай мне лендинг для сервиса доставки.
Выход: Создай лендинг для сервиса доставки.
```

Недопустимый результат:

```text
Создай современный минималистичный адаптивный лендинг для сервиса доставки.
```

## 4. Поведение существующей карточки

| Состояние | Первый селектор | Второй селектор |
|---|---|---|
| Изображение | Изображение | Текущий список image-моделей |
| Видео | Видео | Текущий список video-моделей |
| Вайбкодинг | Вайбкодинг | Codex / Claude / Gemini |

При переключении режима:

- введённый текст сохраняется;
- текущий запрос не отправляется автоматически;
- выбирается модель по умолчанию для нового режима;
- ошибка и состояние `Скопировано` сбрасываются так же, как в текущем сценарии;
- существующие размеры, responsive-классы и визуальные состояния селекторов не меняются.

### Референсные изображения

Чтобы не менять интерфейс, существующий контрол загрузки остаётся в карточке.

Для MVP в режиме `Вайбкодинг`:

- прикреплённый скриншот можно передать как дополнительный контекст;
- очиститель не извлекает из изображения новые продуктовые требования;
- если текст не ссылается на изображение, вложение не должно расширять результат;
- байты и превью остаются только в памяти компонента, как и сейчас;
- лимиты 8 файлов, 10 МБ до обработки, 512 px и JPEG quality 0.7 сохраняются.

## 6. Server API в `opten-website`

### Расширение существующего маршрута

Использовать существующий site-owned endpoint `POST /api/prompt-workbench`, не создавать новый публичный маршрут.

Причины:

- UI уже использует этот transport;
- website JWT и ошибки авторизации уже проверяются;
- сохранится общий кредитный ledger;
- response shape `{ result: { prompt } }` не изменится;
- расширение не зависит от этого маршрута напрямую.

### `api/prompt-workbench.ts`

- расширить `getModelType()` поддержкой `codex`, `claude`, `gemini` → `vibecoding`;
- разделить runtime на две ветки:
  - `image | video` — существующее поведение без изменений;
  - `vibecoding` — отдельный системный prompt и внутренний skill adapter;
- не подключать к coding-запросу текущий image/video `rewriter.md`;
- сохранить JWT verification, body cap, retries, timeout и общую обработку ошибок;
- оставить одну billable operation на явный клик `Улучшить`;
- возвращать `422 no_improvement` и освобождать точную usage reservation при no-op или нарушении guardrails;
- не сохранять prompt, результат или references в Supabase, localStorage или логи.

### Новый server-only prompt

Добавить отдельный файл:

```text
api/_assets/prompt-workbench/vibecoding-cleaner.md
```

Он должен быть site-only и содержать:

- closed-world правило: использовать только смысл исходного текста;
- разрешённые и запрещённые преобразования;
- сохранение языка пользователя;
- дословное сохранение URL, путей, команд, версий, имён API и code identifiers;
- разрешение вернуть текст без изменений;
- требование вернуть только очищенный prompt без пояснений.

Не добавлять этот файл в текущий `sync:prompt-workbench`, пока для него не появится отдельный канонический источник. Image/video `rewriter.md` продолжает синхронизироваться по существующему контракту.

## 7. Тонкие адаптеры Codex, Claude и Gemini

Model-specific слой не меняет смысл и не добавляет обязательные секции.

| Модель | Допустимая адаптация |
|---|---|
| Codex | Прямой императив; уже названные цель и ограничения можно поставить в естественном порядке |
| Claude | Чёткое разделение длинных частей; XML не добавляется автоматически |
| Gemini | Уже указанное критичное ограничение можно поставить раньше остальных частей |

На первом этапе все три модели могут вернуть одинаковый текст. Различие допускается только после benchmark, который докажет пользу без смыслового дрейфа.

## 8. Изменения в `promptscore-proxy`

Существующий `/api/rewrite` всегда добавляет skill-файл по `model_name`. Без отдельного coding-skill он подставит image fallback, поэтому просто отправить `model_name: "codex"` нельзя.

План:

- добавить внутренние непубличные skill-файлы:
  - `skills/_coding-codex.md`;
  - `skills/_coding-claude.md`;
  - `skills/_coding-gemini.md`;
- website endpoint отображает публичные slugs `codex | claude | gemini` во внутренние `_coding-*` slugs;
- файлы с `_` не попадают в публичный `/api/skill?list=1` и недоступны через публичный skill endpoint;
- сохранить существующий `/api/rewrite`, auth, rate limit, atomic reservation и release-on-provider-failure;
- использовать `source: website_vibecoding` и серверную HMAC-подпись, чтобы только сайт мог включить proxy-finalization и release-on-no-op;
- не менять extension request shape и поведение image/video skill-файлов.

## 9. Runtime guardrails

Перед запросом извлечь защищённые фрагменты исходника:

- URL;
- file paths;
- shell/npm-команды;
- версии;
- quoted literals;
- code identifiers и имена API.

После ответа проверить:

1. Результат не пустой.
2. Защищённые фрагменты не исчезли и не изменились.
3. Результат не превышает исходник по длине без допустимой причины.
4. Ответ не содержит преамбул, markdown fences или объяснений.
5. При ошибке parsing/validation возвращается исходный prompt, а операция считается успешно завершённой только если provider уже ответил корректно.

Семантическое равенство нельзя надёжно доказать одной строковой проверкой, поэтому основным quality gate остаётся golden dataset.

## 10. Golden dataset и проверки

Добавить fixture не менее чем из 50 RU/EN примеров:

- уже хороший короткий запрос;
- разговорный и перегруженный запрос;
- повторы;
- UI-задача;
- bugfix;
- refactor;
- задача со стеком, который пользователь указал явно;
- mixed RU/EN с identifiers;
- URL, команды и пути;
- запрос со скриншотом;
- намеренно неполный запрос;
- запрос, который безопаснее вернуть без изменений.

Для каждого fixture зафиксировать:

- обязательные смысловые элементы;
- защищённые буквальные значения;
- запрещённые добавления;
- допустимость no-op;
- пример эталонной очистки.

Критерии прохождения:

- `0` новых продуктовых требований;
- сохранены все обязательные требования;
- `100%` защищённых значений сохранено дословно;
- короткие понятные запросы не расширяются;
- model adapter не меняет семантический набор;
- результат не становится длиннее по умолчанию.

Добавить focused verification script без нового test framework, например:

```text
scripts/verify-prompt-workbench-vibecoding.mjs
```

## 14. Definition of Done

Режим готов, когда:

- в первом селекторе есть `Вайбкодинг` / `Vibe coding`;
- второй селектор показывает Codex, Claude и Gemini;
- интерфейс карточки во всех остальных частях визуально не изменился;
- запрос обрабатывается через отдельный coding cleaner, а не image/video rewriter;
- короткий понятный запрос можно вернуть без изменений;
- golden dataset не фиксирует новых требований или потерю исходного смысла;
- credits/auth/errors работают по текущему website contract;
- prompt и references не сохраняются;
- extension-код и extension UI не затронуты;
- integration contract и agent docs синхронизированы;
- focused checks, build и browser smoke проходят.

## 16. Результат перепроверки плана

Перед реализацией план был сверен с текущими `api/prompt-workbench.ts`,
`promptscore-proxy/api/rewrite.js`, `lib/helpers.js`, публичным `/api/skill` и
контрактом общей кредитной книги. Базовая архитектура подтверждена, но приняты
следующие уточнения:

1. Семантическое равенство нельзя доказать одной строковой эвристикой. Cleaner
   prompt остаётся главным closed-world правилом, а runtime guardrails работают
   как fail-safe внутри proxy: при сомнении отклоняют результат.
2. Ответ провайдера, не прошедший parsing/guardrails, получает
   `422 no_improvement`, не ретраится и освобождает точную atomic reservation.
   Сайт показывает возврат кредита, обновляет баланс и не подменяет платный ответ
   исходным текстом как будто улучшение состоялось.
3. Вложения передаются coding-модели только при явной текстовой ссылке на
   изображение, скриншот, референс или макет. В остальных случаях байты остаются
   только в памяти браузера и не влияют на результат.
4. Golden dataset проверяет 54 RU/EN контрактных кейса, исполняемые guardrails,
   безопасный no-op, protected literals и фактический request adapter через
   локальный mock proxy. Он не делает 54 платных live-запроса и не выдаёт
   статическую проверку за доказательство поведения LLM в продакшене.
5. `opten-website` находится на `main`. Связанный `promptscore-proxy` использует
   текущую основную ветку `master`; ветки не переключались и существующий локальный
   коммит proxy был сохранён.
